# 피그마 링크 분석 → 공통 컴포넌트 생성 로드맵

## 원칙
- 디자인 토큰(색/spacing/radius/fontSize 등) 추가·변경이 필요하면 임의로 수정하지 않고 먼저 질문한다.

## 0. 준비
- `figma-design-to-code` 스킬 로드 후 `get_design_context` 호출 (직접 호출 금지)
- 링크가 여러 화면을 담고 있으면 `get_metadata`로 전체 구조부터 훑고 공통 컴포넌트 후보 스캔

## 1. 후보 추출 — 진짜 공통인지부터 판별
- Figma에서 이미 컴포넌트/컴포넌트 셋으로 등록된 것(버튼, 인풋, 카드, 뱃지, 아바타 등)을 1순위로 봄
- 컴포넌트로 안 묶여 있어도 2개 이상 화면에서 반복되는 레이아웃이면 후보에 포함
- 화면 1곳에만 나오는 요소는 제외 (YAGNI — 나중에 두 번째 사용처 생기면 그때 뽑음)

## 2. 토큰 대조
- `get_variable_defs`로 Figma 변수 확인 → `tailwind.config.js`에 이미 있는 색/spacing/radius/fontSize 토큰과 매칭
- 이미 커버되면 새로 안 만듦, 빠진 값이 있으면 추가/변경 전 사용자에게 먼저 질문

## 3. 컴포넌트별 스펙 정리
- 각 후보마다 variant 축(size, color, state: disabled/pressed 등) 정리
- `tailwind-variants`로 variant 정의 → `src/components/`에 RN 컴포넌트로 구현

## 4. 구현 순서
- 의존성 없는 원자 컴포넌트(Badge, Avatar 등) 먼저 → 그걸 쓰는 조합 컴포넌트(Card 등) 나중
- 기존 토큰 재사용, 하드코딩 값 금지

## 5. 검증
- 컴포넌트별 최소 self-check (타입 에러 없는지 + 간단한 렌더 확인용 스크린 하나)
- 필요하면 Code Connect로 Figma 컴포넌트 ↔ 코드 매핑 등록 (선택)

## Skip
- Storybook/디자인시스템 문서화 전체 세팅 → 컴포넌트 수가 늘어나서 필요해질 때 추가

## 6. 5종 구현 순서 (Text / Button / Input / Card / Avatar)

의존성 기준 정렬 — 다른 컴포넌트 안에서 쓰이는 것부터, 여러 개를 조합하는 것은 마지막:

1. **Text** ✅ (`src/components/Text.tsx`) — 다른 4종이 전부 내부적으로 텍스트를 씀. `fontSize`/`fontFamily` variant만 감싸는 가장 얇은 레이어라 제일 먼저. 기존 토큰만으로 커버되어 Figma 재조회 없이 진행(2단계 원칙: 이미 커버되면 새로 안 만듦).
2. **Avatar** ✅ (`src/components/Avatar.tsx`) — 완전 독립. Figma 노드 24:495(커뮤니티/게시글 상세, 34px)·24:3016(마이페이지, 48px) 확인 → 동일 플레이스홀더 아이콘의 sm/lg 두 사이즈로 판단, `size` variant로 반영. 아이콘 자산은 `assets/icons/avatar-placeholder.svg`로 다운로드·커밋. 배경색 Figma `#F5F5F5`가 기존 토큰과 불일치해 사용자에게 질문 → `background.circle` 신규 토큰 추가로 결정.
3. **Button** ✅ (`src/components/Button.tsx`) — Text에 의존. Figma에서 CTA 버튼(24:2033 등, 320×56, radius 16, `bg-primary`+`text-inverse`)과 이전/다음 분할 버튼(24:2298/2301, `bg-border-strong`+`text-default`)을 스캔 → `variant: 'primary'|'secondary'`, 둘 다 기존 토큰과 정확히 일치해 신규 토큰 없음. `disabled`는 `opacity-40`(기본 Tailwind opacity 스케일, 별도 토큰 불필요)으로 처리.
   - **Deferred:** outline 버튼(`나가기`, 24:798)과 밑줄 텍스트 링크(`인증 번호 재발송`, 24:2063 등)도 발견했지만 보류 — outline은 클럽 단톡방 화면 1곳에서만 확인되어 YAGNI로 제외(다른 화면에 재등장하면 추가), 텍스트 링크는 여러 화면에서 반복되긴 하나 색상(`#575858`)이 기존 토큰과 안 맞아 별도 확인 필요 + Button보다는 별도 컴포넌트(TextLink류)에 가까워 범위 밖으로 판단. 필요해지면 그때 사용자에게 토큰 확인 후 추가.
4. **Input** ✅ (`src/components/Input.tsx`) — Text에 의존. Figma "클럽 이름"(24:939, 아이콘 없음)·로그인 ID/PW 필드(24:1916/24:1925, 왼쪽 아이콘) 스캔 → `label`/`required`/`error`/`leftIcon` prop으로 정리. 박스 스타일(`border-border-strong`, `rounded-md`, `bg-background`, h-56)은 전 화면에서 토큰과 정확히 일치. placeholder 색은 Figma의 `text-muted` 60% 투명도 값(`rgba(109,122,116,0.6)`)을 그대로 사용(새 값 아님, RN `placeholderTextColor`는 className으로 못 줘서 하드코딩).
   - **토큰 질문:** 에러 메시지 색이 화면마다 3가지(`#f30707`/`#ba1a1a`/`#e56d6d`)로 달라 사용자에게 확인 → 기존 `danger` 토큰(`#f30707`) 통일 사용으로 결정.
   - **Deferred:** 비밀번호 눈 아이콘 토글(보기/숨기기 버튼), 인원수 스테퍼(+/-), 날짜 스피너(mm/dd/yyyy) — 전부 특정 화면 1곳 전용의 특수 위젯이라 YAGNI로 제외. 체크박스로 보이는 "Input"이라는 이름의 사각형 노드들은 실제로는 별도 Checkbox 컴포넌트(5종 목록 밖)라 무시.
5. **Card** ✅ (`src/components/Card.tsx`) — 컨테이너 셸만 담당(children 조합은 화면 구현 시점/Phase 4에서). Figma "Article Card"(24:493, radius 16)·"Club Join Card"(24:635, radius 20)·"Comment Card" 등 비교 → 공통 셸(흰 배경+테두리+radius+padding)은 같고 radius만 다름 → `radius: 'lg'|'xl'` variant.
   - **토큰 질문 2건:** (1) 그림자 값이 `boxShadow` 카테고리 자체가 config에 없어 물어봄 → 그림자 생략(테두리+배경만). (2) 카드마다 테두리색이 `#dee4e0`/`#bccac3`로 갈려 물어봄 → 기존 `border.strong`로 통일(`border-border-strong/30`).

## 진행 상황: 5종 전부 완료 (2026-08-16)
Text / Avatar / Button / Input / Card 모두 `src/components/`에 구현, 전부 `tsc --noEmit` 통과. Deferred 항목(outline 버튼, 텍스트 링크, 비밀번호 눈 토글, 스테퍼, 날짜 스피너 등)은 필요해지는 화면 구현 시점에 재검토.

각 컴포넌트는 **한 번의 요청 = 한 컴포넌트**로 진행(CLAUDE.md 작업 방식 원칙). 순서대로 가되, 특정 컴포넌트의 Figma 노드가 애매하면 건너뛰고 다음 걸로 — 순서 고정보다 진도 우선.

`tailwind.config.js`에는 이미 color/spacing/radius/fontSize/fontFamily 토큰이 충분히 있음 — 5종 모두 새 토큰 없이 커버될 가능성이 높지만, 컴포넌트별 Figma 값 대조는 각자 진행 시점에 확인(2단계 원칙 그대로 적용).
